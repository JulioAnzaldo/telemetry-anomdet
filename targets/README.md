# Target ports

The distilled detector generated by `telemetry_anomdet.models.deep.codegen` is
plain C99: no allocation, no platform APIs, no intrinsics. That is what lets one
set of generated sources build for a host, a microcontroller, or a flight
processor without modification.

Everything platform specific lives here, one directory per target. **Nothing in
this directory may leak back into the generated sources.**

## Generating the sources

Each target expects the generated detector in its own `generated/` directory:

```
python examples/export_kangdn_c.py targets/host/generated
python examples/export_kangdn_c.py targets/esp32s3/main/generated
```

That writes three files:

| File | Contents |
| --- | --- |
| `kangdn.h` | Interface: dimensions, status codes, two entry points |
| `kangdn.c` | Parameters as `static const`, plus the scoring path |
| `kangdn_vectors.h` | Golden vectors: input windows, expected scores, expected flags |

The vectors header is what makes a port checkable on the device itself. It
carries the reference evaluator's output for each window, so the target proves
its own correctness without any host tooling in the loop.

## Editor diagnostics before generating

An editor will report unresolved includes in each port's `main.c` until the
sources are generated, because `generated/` is not checked in. One unresolved
header makes every symbol it declares look undeclared, so a single missing
include path shows up as twenty or more problems. The ESP32-S3 port reports the
same for the ESP-IDF headers, which resolve only through the framework's include
paths.

Neither affects the build. Run the export, and for the ESP-IDF port generate a
`compile_commands.json` from the build system if the diagnostics are a
distraction.

## What a port must do

A target is complete when it does three things and reports three results.

1. **Compile clean** under the strictest warnings the toolchain supports. The
   host build uses `-std=c99 -O2 -Wall -Wextra -Werror -pedantic`.
2. **Match the golden vectors.** Scores within the generated tolerances, and
   anomaly flags exactly. The flag is the decisive check: a score may drift in
   its last digits at single precision, but the flag is what the rest of the
   system acts on.
3. **Report timing and memory**: microseconds per window, and evidence that
   scoring allocates nothing.

`targets/host/` is the reference implementation of those three checks. A new
target should be a copy of its `main.c` with the timing call and the output
mechanism swapped.

## Tolerances, and why an absolute term is needed

The comparison is `|got - want| <= atol + rtol * |want|`.

The deviation score is a difference of differences: a forecast error is
`|prediction - target|`, and the score normalises that against the training
median. When a score is small compared with those intermediate magnitudes, two
rounds of cancellation leave it with large *relative* error at single precision
while its *absolute* error stays negligible. A pure relative tolerance therefore
fails on exactly the scores that matter least, which is why both terms are
generated.
